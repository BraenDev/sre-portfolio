Automated Service Remediation

A remediation engine that closes the loop project #1 left open. When a service goes UNHEALTHY it acts: pulls the node from traffic, restarts the service, verifies health, and either restores it or escalates to a human — with attempt limits, cooldowns, and a verify-before-serve gate so the automation can never make things worse. Modeled directly on the production incident workflow I ran at AestheticsPro.

Business / reliability problem

At AestheticsPro, a Lucee web node going unhealthy meant a human worked this runbook by hand, usually under pressure:

  1. Remove the node from the load balancer
  2. Restart the Lucee and WWW services
  3. Verify application health
  4. Return the node to the load balancer
  5. Confirm service, document, notify stakeholders

Every step is mechanical, every minute of it is toil, and a tired operator can skip step 1 or botch step 3. This project automates the runbook — and, more importantly, automates the judgment around it: when to act, when to wait, and when to stop and call a human.

Architecture

One run of the remediator makes one decision. Designed for a scheduler (cron / systemd timer):

  1. Check — probe the health endpoint; classify HEALTHY / DEGRADED / UNHEALTHY.
  2. Decide — HEALTHY: reset failure count. DEGRADED: log, no action. UNHEALTHY: continue.
  3. Gate — lock file present? Stop. Cooldown active? Stop. Attempts exhausted? Escalate.
  4. Isolate — remove the node from the pool before touching the service.
  5. Restart — stop (graceful, then SIGKILL if needed), start fresh, track the PID.
  6. Verify — poll health up to 5 times. Only a verified-healthy node returns to the pool.
  7. Restore or escalate — recovered: back to the pool, counters reset. Still down: node stays out of the pool, failure recorded; at the attempt limit, CRITICAL escalation.

The load balancer is simulated as pool.json — a deliberate lab simplification. What's real is the ordering: traffic is never served from an unverified node, and a failed remediation fails safe (node stays out), never open.

Technologies

Python 3, the requests library, and the standard library (subprocess, json, logging, signal). The demo patient is a 30-line http.server with a /health endpoint — real enough to kill and restart, simple enough to reason about.

Implementation

Full source: BraenDev/sre-lab (python/remediate.py, python/demo_service.py). The remediation cycle — isolate, restart, verify, restore-or-hold:

def remediate(state):
    # 1. Isolate: take the node out of traffic BEFORE touching it.
    remove_from_pool()

    # 2. Restart.
    stop_service()
    start_service()

    # 3. Verify before serving traffic again. Never return an
    #    unverified node to the pool.
    if verify_health():
        return_to_pool()
        return True

    log("leaving it OUT of the pool (fail safe, not fail open)")
    return False

And the decision gates that run before any action is taken:

if os.path.exists(LOCK_FILE):        # manual override -- a human is in charge
    return 0                           # take no action at all
if state["consecutive_failures"] >= MAX_ATTEMPTS:
    log(CRITICAL, "... ESCALATING, human intervention required")
    return 2
if time.time() - state["last_attempt"] < COOLDOWN_SECONDS:
    log(WARNING, "In cooldown -- skipping remediation")
    return 1

Reliability design

The guards are the project. Automation without them is how you turn one failed node into a restart storm:

  • Attempt limit (3). Consecutive failed remediations escalate to CRITICAL and stop. The script exits 2 — a scheduler can page on that.
  • Cooldown (120 s). Minimum gap between attempts; a second run inside the window skips remediation instead of hammering a dying service.
  • Verify-before-serve. Up to 5 post-restart health polls; the node returns to the pool only on a verified HEALTHY.
  • Fail safe. If verification fails, the node stays out of the pool. Reduced capacity is better than serving errors.
  • Manual override. A remediation.lock file disables all action — for maintenance windows or when a human wants the wheel.
  • DEGRADED is not UNHEALTHY. Slow-but-working services are logged, never restarted. No restart storms over latency.

Observability

Every decision is logged with a timestamp, and the exit code tells a scheduler what happened: 0 healthy or no action needed, 1 unhealthy (handled, failed, or cooling down), 2 escalated — page a human. pool.json and remediation_state.json are inspectable at any moment: who is serving traffic, how many failures in a row, when the last attempt ran.

Failure test

Two controlled failures, both executed for real:

  1. Crashed service. Killed the demo service process, then ran the remediator.
  2. Unrecoverable service. Pointed the start command at a nonexistent script (simulating a corrupted deployment), with the attempt limit lowered to 1 — forcing the escalation path.

Detection

The killed service refused connections; the prober classified it UNHEALTHY in ~2 ms and the remediation cycle began on the same run. No separate monitoring layer needed for the lab — detection and response live in one auditable flow.

Recovery

Results

All five behaviors verified by execution, not by reading the code:

  • Healthy service → exit 0, zero action taken.
  • Crashed service → detected, isolated, restarted, verified HEALTHY, returned to pool.
  • Unrecoverable service → node held out of the pool, failure counted.
  • Attempt limit reached → CRITICAL escalation, exit 2.
  • Lock file present → manual override, no action, exit 0.

The log file tells the same story independently — every console line above has a matching timestamped entry in logs/remediation.log, with severity mapped to the seriousness of the event.

Repository & runbook

Source: BraenDev/sre-lab (python/remediate.py, python/demo_service.py, python/REMEDIATION_LAB.md).

Mini-runbook — "remediator escalated (exit 2)":

  1. Check pool.json — the node is already out of traffic; blast radius is contained.
  2. Read logs/remediation.log — the last ERROR lines show what restart attempts did.
  3. Check demo_service.log — the service's own output often names the cause.
  4. Fix the underlying issue, delete the stale state if needed, remove any lock file, and let the next scheduled run verify recovery.

Production considerations

What would change before this touched real production:

  • Real load-balancer integration — API calls to the LB instead of a JSON file, with the same isolate-before-touch ordering.
  • Process supervision — systemd units instead of PID files; PID files are a lab convenience.
  • Alerting hooks — webhook/PagerDuty on escalation, not just an exit code and a log line.
  • Configuration file — targets, thresholds, and commands belong in config, not constants.
  • Richer health signals — beyond HTTP 200: error rates, saturation, dependency checks.
  • Change safety — the restart step in production would be a rolling deploy, not a kill-and-start.
